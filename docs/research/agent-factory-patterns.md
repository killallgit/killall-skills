# Coding-agent factory patterns

Research date: 2026-10-15. Scope: durable work tracking for the agents generated by `skills/agent-setup`. This note distinguishes documented mechanisms from the design proposed below. Only primary documentation and source were used; nothing was installed or benchmarked.

## What the examples establish

There is substance behind the factory idea: work survives individual agent sessions, has explicit ownership and dependencies, and needs evidence before completion. These projects implement different parts of that idea; they do not establish a universal factory standard.

| Example | Useful mechanism | Fit here |
| --- | --- | --- |
| Gas Town + Beads | Persistent task graph, claims, worker identity, recovery, merge queue | Strong example of a full operating system around agents; substantial infrastructure |
| GSD Core | Plans, dependency waves, summaries, verification and session handoffs | Closest to our existing lane workflow |
| Anthropic harnesses | Structured feature checklist, progress journal, Git history, repeatable startup checks | Small baseline for continuity across contexts |
| Claude Agent Teams | Native shared tasks, dependency blocking, locked claiming | Convenient Claude adapter, with experimental and session limits |
| OpenAI Symphony | Tracker-driven scheduler and isolated runs | Concrete example of the separate coordinator/worker runner discussed earlier |

The rows summarize the sources examined in the sections below, not comparative performance results.

## Gas Town and Beads: work is independent of the worker

Gas Town coordinates workers through persistent assignments and a Beads ledger. Its Witness detects stuck workers; its Refinery manages verification and integration. These are separate responsibilities from writing code. Adopting the full system also brings runtime and storage dependencies such as Dolt and, for its managed sessions, tmux. [Gas Town README](https://github.com/gastownhall/gastown)

The lifecycle documentation explicitly separates **identity**, **sandbox/worktree**, and **session**. Sessions can rotate during an assignment while the worktree remains. Clean completion retires the live session and preserves branch/merge-request evidence for subsequent cleanup and merging. A stalled session and completed work awaiting integration are different states. [Polecat lifecycle](https://github.com/gastownhall/gastown/blob/main/docs/concepts/polecat-lifecycle.md)

A convoy persists as the tracking unit while its current set of workers is ephemeral. This distinction is directly useful here: a lane must retain its identity when a builder is replaced. [Convoy concept](https://github.com/gastownhall/gastown/blob/main/docs/concepts/convoy.md)

Beads supplies dependency-aware ready work and `bd update <id> --claim`, documented as atomically setting assignee and `in_progress`. Current Beads uses Dolt: embedded mode is single-writer; server mode supports concurrent writers. Its JSONL file is an export, not the authoritative store or a backup. Therefore, older descriptions of “a Git-backed JSONL task file” are insufficient for choosing today's architecture. [Beads commands and storage modes](https://github.com/gastownhall/beads)

Persistence also has levels: Gas Town's default root-only workflow reads steps as an inline checklist; poured workflows materialize checkpoint steps so completed steps survive session death. Merely calling a workflow “persistent” does not prove every intermediate step is recoverable. [Molecule lifecycle](https://github.com/gastownhall/gastown/blob/main/docs/concepts/molecules.md)

## GSD: durable artifacts around a lean coordinator

The former `gsd-build/get-shit-done` repository is archived and points to Open GSD's GSD Core. The current project describes a discuss/plan/execute/verify/ship loop, with heavy work in fresh subagents and persistent context artifacts. [Migration notice](https://github.com/gsd-build/get-shit-done), [GSD Core](https://github.com/open-gsd/gsd-core)

GSD records project state in `.planning/STATE.md`, execution instructions in per-plan `PLAN.md`, outcomes in `SUMMARY.md`, and independent verification in `VERIFICATION.md`. Its architecture documents lockfile exclusion around shared state writes, including atomic exclusive lock creation and stale-lock handling. That is an actual concurrent-write mechanism; “each agent updates the Markdown” alone is not. [GSD architecture](https://github.com/open-gsd/gsd-core/blob/next/docs/ARCHITECTURE.md)

Its execute workflow groups plans into dependency waves and reconciles filesystem/Git artifacts with agent completion signals. It explicitly handles Codex runs that terminate abnormally after committing: the session's terminal state does not by itself determine task success. Its safe-resume gate also detects commits without the expected summary before redispatch, avoiding accidental duplicate implementation. These mechanisms are workflow/source evidence, not a measured guarantee of recovery correctness. [Execute-phase workflow](https://github.com/open-gsd/gsd-core/blob/next/gsd-core/workflows/execute-phase.md)

Pause writes a structured `HANDOFF.json`; resume restores position and decisions. State validation/synchronization reconstructs tracking from disk rather than requiring the model to trust stale prose. This is useful for our restart behavior even without adopting the entire framework. [Recovery guide](https://github.com/open-gsd/gsd-core/blob/next/docs/how-to/recover-and-troubleshoot.md)

## Anthropic: a small baseline, plus a concurrency example

Anthropic's long-running harness uses an initializer and subsequent coding sessions. A structured JSON feature list contains test steps and passing status; a progress file and Git commits support continuity. Each session reads the artifacts and recent history, checks that the application still works, and advances one feature. Passing requires testing, rather than the agent merely announcing completion. The article explicitly leaves the best multi-agent architecture as an open question; it is not evidence that a large agent factory is always better. [Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)

Its compiler experiment adds concurrency with task files claimed through Git synchronization: agents use isolated clones, claim before implementing, then synchronize and release the claim. The author calls it an early prototype and says it has no orchestration agent. The lesson is narrower than “use lock files”: a shared authority must reject competing claims; separate worktrees containing independent copies of a file do not provide that by themselves. [Building a C compiler](https://www.anthropic.com/engineering/building-c-compiler)

## Native tasks and a separate runner

Claude Agent Teams supports pending/in-progress/completed tasks, dependency blocking, and file locking to prevent duplicate claims. Task lists persist locally for resumed sessions, subject to retention; team runtime directories are removed on session end. It remains experimental, does not restore in-process teammates on resume, and documents possible task-status lag. Completion hooks can reject a task transition. This is a useful host adapter, not a cross-host durable project ledger. [Claude Agent Teams](https://code.claude.com/docs/en/agent-teams#assign-and-claim-tasks)

OpenAI Symphony is an engineering preview of a tracker-driven runner. Its draft specification separates an issue, a run attempt, and a live agent session; uses per-issue workspaces and versioned `WORKFLOW.md` policy; and specifies concurrency bounds, retries, and reconciliation. Scheduler claims/running/retry maps are in memory, with recovery from tracker and filesystem state rather than a restored scheduler database. A successful agent run can stop at Human Review instead of marking the issue Done. [Symphony overview](https://github.com/openai/symphony), [draft specification](https://github.com/openai/symphony/blob/main/SPEC.md)

## Recommendation and possible next steps

The implemented baseline keeps four roles and a small durable lane protocol: the [orchestrator](../../skills/agent-setup/templates/orchestrator.tmpl.md) defines dependencies and review gates, each [builder](../../skills/agent-setup/templates/builder.tmpl.md) persists its lane JSON in one shared global folder, and the [reviewer](../../skills/agent-setup/templates/reviewer.tmpl.md) returns independent evidence. The [state guide](../../skills/agent-setup/templates/state.md) defines the current minimal schema. The richer records, transitions and tracker operations below are future proposals, not implemented behavior.

Each lane record should carry:

- Stable task ID, acceptance checks, dependencies and allowed files.
- Owner plus attempt/session ID, absolute worktree, branch and base commit.
- State, last update, next action and blocker reason.
- Result commit; gate command/result; reviewer verdict and evidence; hall-monitor result.

Use `queued → running → review → ready → integrated`, with an explicit blocked reason and retry attempt. Keep “ready” separate from integration because our current templates integrate only when requested. Agent `idle`, `exited` and `failed` are execution observations, not lane verdicts. Bind every review to the exact result commit; new implementation invalidates older review evidence.

Write updates at claim/start, meaningful checkpoints, block, handoff and finish. Record what changed and the next action; token-by-token activity diaries would add noise without proving progress.

Start with **one authorized tracker writer** receiving structured worker reports. Put the tracker at one canonical location visible from every worktree. A JSON/Markdown format is a reasonable first version only with serialized ownership; allowing workers to self-claim later requires a transactional/locked operation with conflict detection. Do not silently give every worktree an independent board.

Preserve the orchestrator's restricted tools. Give it narrow tracker operations, or delegate persistence to the designated writer; restoring broad shell/edit access would undermine its separation from implementation. Host adapters can translate reporting/delegation calls while sharing the task schema and transition rules. Setup updates should refresh generated definitions without overwriting project task history.

On restart, reconcile the record against worktree identity, uncommitted changes, commits and review artifacts before retrying. A missing heartbeat alone should flag attention, not trigger a second simultaneous owner. Begin without autonomous watchdogs, dashboards or another model role; add those only when real usage demonstrates the need.

Not checked: installation, live multi-agent runs, throughput, costs or failure-injection recovery. Documentation describes intended behavior; operational reliability and cross-host permission enforcement still require a focused implementation test.
