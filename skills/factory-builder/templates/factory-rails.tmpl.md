# Factory

You are the `orchestrator` for this session. Read the installed orchestrator agent and apply it: `.claude/agents/orchestrator.md`, `.cursor/agents/orchestrator.md`, or `.codex/agents/orchestrator.toml`, whichever this host uses. Do not spawn a second orchestrator. This skill is the job procedure. The orchestrator agent is how you brief, verify, and report.

{{structure}} owns how work is shaped in this repository: specs, plans, issues, docs, and reviews. This skill is the rails around running that work in parallel. Use {{structure}}'s skills for every stage they cover, and leave their artifacts where they put them. `.factory/` holds lane state only.

This file is generated by factory-builder. Re-run that skill to change it, so the copies under `.agents/`, `.claude/`, and `.cursor/` stay identical.

## Loop

```text
work (spec, plan, tickets, or a feature)
  → spec from {{structure}}
  → lanes cut from the spec
  → one builder per independent lane, in parallel, each in its own worktree
  → gate and diff checked by you, per lane
  → review per lane, in parallel
  → ready, waiting for /factory approve
```

## State

`.factory/board.json` is the board. You are the only writer. Each entry is one lane.

```json
{
  "jobs": [
    {
      "id": "001-example-api",
      "job": "001-example",
      "source": "path or issue of the spec",
      "branch": "factory/001-example-api",
      "depends_on": [],
      "stage": "build",
      "round": 1
    }
  ]
}
```

Stages: `spec`, `build`, `review`, `ready`, `needs-human`. While a job is still being shaped it has one entry, with the job id, at stage `spec`.

Write each builder's final message to `.factory/jobs/<lane-id>/build.md` and each review to `.factory/jobs/<lane-id>/review-<round>.md` as soon as it returns.

## Commands

- `/factory <work>` — build that work. It may be a {{structure}} spec, plan, ticket list, or issue, or a feature that has none yet.
- `/factory approve <job-id>` — integrate that job's `ready` lanes onto `{{default_branch}}`.
- `/factory rework <lane-id> <note>` — send the note to that lane's builder and set its stage back to `build`.

## 1. Get the spec

Number the job `NNN-slug`, one past the highest job number on the board, starting at `001`. Add it to the board at stage `spec`.

When the work is already a {{structure}} artifact, read it. Otherwise produce one now. {{spec_tool}}

Record the spec's location as the entry's `source`. Done when the spec exists where {{structure}} keeps it and every acceptance check in it can fail a test or a person. Ask the user when an acceptance check cannot.

## 2. Cut lanes

Cut the spec into lanes, as the orchestrator's Delegation section says. When {{structure}} already cut the work into tickets or tasks, start from one lane per ticket.

- Two lanes that edit the same file become one lane, or one depends on the other.
- A contract two lanes share goes into both briefs, word for word.
- A lane that needs another lane's code lists it in `depends_on`.
- One lane is a fine answer. Say so when the work never needed parallelism.

Replace the job's `spec` entry with one entry per lane: id `<job-id>-<slug>`, branch `factory/<lane-id>`, stage `build`, round `1`.

Done when every acceptance check belongs to exactly one lane, and no two lanes without a dependency edit the same file.

## 3. Build in parallel

For every lane whose `depends_on` is empty or already integrated, create its worktree as the git and worktree note says, then spawn all of those builders in one message. Each brief names the worktree, the branch, the spec location, the acceptance checks this lane owns, the files it may touch, and the gate `{{gate}}`.

As each builder returns, write its report, then check it yourself: run `{{gate}}` in that worktree and read the diff. Reproduce a reported blocker before you re-plan. Continue the same builder to correct it. Move a verified lane to `review`.

A lane that depends on another starts after `/factory approve` has integrated the one it needs, from the new `{{default_branch}}`.

Done when every started lane has a commit you ran the gate on, or sits at `needs-human` with the reason in its build file.

## 4. Review

Review each lane at `review` as soon as it gets there, in parallel with the others. Spawn a read-only sub-agent per lane. Brief it with the spec location, the lane's acceptance checks, and `git diff {{default_branch}}...factory/<lane-id>`. {{review_tool}} It returns PASS or CHANGES with findings.

On CHANGES with round under 2, increment the round, continue the same builder with the findings, and return that lane to step 3. On CHANGES after round 2, set the lane to `needs-human`. On PASS, set it to `ready`.

When two lanes meet at a contract, read that seam yourself before either is `ready`. Neither lane was looking at it.

Done when every lane is `ready` or `needs-human`.

## 5. Approve

`/factory approve <job-id>` integrates that job's `ready` lanes, one at a time, dependencies first. For each lane:

1. In the lane's worktree, rebase `factory/<lane-id>` onto `{{default_branch}}`.
2. Run `{{gate}}` there.
3. Fast-forward `{{default_branch}}` to the lane.

Use the merge method in the git and worktree note in place of these three when it sets one. Stop at the first lane that fails, and report it. Push only when the user asks. When {{structure}} has a ship skill and the user asks to ship, hand the integrated branch to that skill. Remove each integrated lane's worktree as the note says, and its entry from the board, then start any lane that was waiting on it.

Done when every `ready` lane is on `{{default_branch}}` and the gate passes there, or you have reported the lane that stopped it.
