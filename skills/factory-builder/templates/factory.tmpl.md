# Factory

You are the `orchestrator` for this session. Read the installed orchestrator agent and apply it: `.claude/agents/orchestrator.md`, `.cursor/agents/orchestrator.md`, or `.codex/agents/orchestrator.toml`, whichever this host uses. Do not spawn a second orchestrator. This skill is the job procedure: which agent runs, which file you write, and when the stage changes. The orchestrator agent is how you brief, verify, and report.

This file is generated by factory-builder. Re-run that skill to change it, so the copies under `.agents/`, `.claude/`, and `.cursor/` stay identical.

## Loop

```text
feature
  → spec-writer
  → builder on factory/<job-id>
  → reviewers ({{lenses}}) in parallel
  → builder again while any verdict is CHANGES (two review rounds at most)
  → approver
       APPROVE  → ready, waiting for /factory approve
       ESCALATE → needs-human
```

Agents in this factory: `spec-writer`, `builder`, {{lenses_agents}}, `approver`.

A review round is complete when `.factory/jobs/<id>/round-<n>/` has one `review-<lens>.md` per lens ({{lenses}}). Start the next step only then.

## State

`.factory/board.json` is the board. You are the only writer.

```json
{
  "jobs": [
    {
      "id": "001-example",
      "branch": "factory/001-example",
      "stage": "review",
      "round": 1,
      "reviews": { "code": "PASS", "security": "pending" }
    }
  ]
}
```

Stages: `spec`, `build`, `review`, `ready`, `needs-human`.

Job files, also only yours:

```text
.factory/jobs/<id>/spec.md
.factory/jobs/<id>/build.md
.factory/jobs/<id>/round-<n>/review-<lens>.md
.factory/jobs/<id>/decision.md
```

Write an agent's final message into its file as soon as it returns. Reviewers, the spec writer, and the approver are sandboxed so they can return text and cannot file it themselves.

## Commands

- `/factory <feature>` — open a job for that feature.
- `/factory next` — open a job for the first unchecked `- [ ]` line in `.factory/backlog.md`.
- `/factory approve <job-id>` — fast-forward the job branch onto `{{default_branch}}` when the job is `ready`.
- `/factory rework <job-id> <note>` — send the note to the builder and set the stage back to `build`.

## 1. Open the job

Number the job `NNN-slug`, one past the highest existing `.factory/jobs/` directory, starting at `001`. The slug is a few hyphenated words from the feature.

Create branch `factory/<job-id>` from `{{default_branch}}` using this repository's existing worktree pattern. Add the job to `.factory/board.json` at stage `spec`, round `1`, reviews pending for each lens. Done when that branch exists in the checkout the pattern names and the board lists the job.

## 2. Specify

Spawn `spec-writer` with the feature, the job id, and the conventions in {{conventions}}. Write its message to `.factory/jobs/<id>/spec.md`. Move the stage to `build`. The spec-writer already carries the installed spec-tool instruction.

Done when `spec.md` starts with a heading and has acceptance checks.

## 3. Build

Spawn `builder`. The brief names the worktree path, the branch, the spec path, and the gate `{{gate}}`. On a rework or a CHANGES round, include the note or the round directory and tell it to continue the same work.

Continue the same builder session when the host allows it. When it does not, spawn `builder` again with the spec, the branch, and the previous build report.

Write the build report to `.factory/jobs/<id>/build.md`. Re-run `{{gate}}` yourself in the worktree, and read the diff, before you treat the report as true. A reported blocker gets the same check: reproduce it before you re-plan. Move the stage to `review`. The builder already carries the installed implement-tool instruction.

Done when the branch has a commit and you have run the gate yourself.

## 4. Review

Spawn every review agent together: {{lenses_agents}}. Each brief names the spec, the branch, and `git diff {{default_branch}}...factory/<job-id>`. Each reviewer already carries the installed review-tool instruction.

Write each message to `.factory/jobs/<id>/round-<n>/review-<lens>.md`. Update that lens on the board as each file lands.

When any verdict is CHANGES and the round number is under 2, increment the round, set the stage to `build`, and return to step 3. When any verdict is still CHANGES after round 2, write the reason into `decision.md`, set the stage to `needs-human`, and stop. When every verdict is PASS, go to step 5.

Done when every lens has a file in the round directory and the board matches those verdicts.

## 5. Decide

Spawn `approver` with the spec, the build report, and the review files. Write its message to `.factory/jobs/<id>/decision.md`.

`APPROVE` sets the stage to `ready`. `ESCALATE` sets it to `needs-human`. Leave the branch unmerged either way.

Done when `decision.md` starts with `APPROVE` or `ESCALATE` and the board stage matches.

## 6. Approve

`/factory approve <job-id>` applies only to a `ready` job.

```bash
git checkout {{default_branch}}
git merge --ff-only factory/<job-id>
```

When fast-forward fails, stop and report. Leave the branch in place. Push only when the user asks. Remove the job worktree the same way this repository usually removes one, and the job's entry from the board.

Done when `{{default_branch}}` contains the job commit, or you have reported why the merge did not happen.

## Board

From `.factory/`, `python3 -m http.server` serves `dashboard.html`. It polls `board.json`.
